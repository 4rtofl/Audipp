# 再生主体の切替

[#61](https://github.com/4rtofl/Audipp/issues/61) は FR-PLY-03/07、FR-NET-03、DD-QUEUE-04、TEST-QUEUE-01 のうち、再生主体の停止確認、取消、遅延応答を扱う。

- `PlaybackOwnerCoordinator` は再生側の単一ルーパー上で、現在の主体、遷移ID、キューと項目ID、revision、次の要求を管理する。アダプターは開始・停止の結果を同じルーパーへ通知する。開始や停止のコマンド受理は観測結果と区別する。
- `onStopped(token)` は、対応する非再生状態を観測し、旧主体に送信済みの停止・取消コマンドが後続の再生に作用しないことを保証できる時点で通知する。この保証がSDKから得られない場合、アダプターはコマンドの終端と非再生状態の観測を独立に待ち、観測が有効な状態で両方が揃ってから通知する。非再生を観測できず、コマンドの安全性だけを確認できた場合は `onStopCommandsSettled(token)` で知らせる。いずれも最新の停止トークンを使い、過去の試行で発行したコマンドも含めて保証する。
- 旧開始の終端と `onStopped` が揃ったら次へ進む。キューrevisionの読み取り完了後、効果を発行する同じルーパーの処理内で、キューの現在revisionと `SourceResolver` の許諾・経路・遷移・記述子を中断なしで照合する。現在のrevisionと許諾は、更新が同じルーパーで直列化された値を参照し、取得できない場合は開始を拒否する。読み取りの想定内の失敗は `Result.failure` で返す。失敗時は要求を終了し、コルーチンの取消は伝播する。開始後は再生を観測して初めて `ACTIVE` にする。
- Stop・別曲・項目削除・経路変更の際は保留中の開始を破棄する。取消後に古い開始の成功が届いたら、別の照合トークンで停止を再要求する。旧開始の応答が未確定の間は次の開始を保留する。同じSDKで古い再生を止める操作が、新しい要求まで止めることを防ぐためである。
- 確認の期限はCoordinatorのスコープで管理する。期限切れでは保留要求を失効させ、旧主体の追跡を続ける。遅れて解放できた場合も、失効した要求から開始や引き渡しを発行しない。 `STOP_UNCONFIRMED` では `retirement` に、停止観測、旧開始の終端、旧コマンドの安全性を個別に公開する。
- 旧開始の応答が失われた場合、アダプターは独立した失効確認により、その開始が現在の再生を残さず今後も再生を発生させないことを保証できれば `onStartAborted` を通知できる。通常の停止確認条件はその場合も適用する。保証が得られない間は `retirement.startSettled` が `false` のままで、利用者の手動停止だけでは継続できない。停止観測を得られない場合は、旧開始が終端し、かつ旧コマンドが後続に作用しないことを確認できれば、利用者の手動停止と継続確認で解放できる。その遷移IDは `lastUnverifiedStop` に保持する。期限切れで失効した要求は改めて送る必要がある。
- 外部アプリへの引き渡しは利用者の明示操作を待ち、再検査してから開く。引き渡し後の再生状態は `ACTIVE` に更新しない。

`PlaybackOwnerCoordinatorTest` で、停止コマンドの受理・非再生状態の観測・コマンドの終端が別々に届く切替、旧開始の終端通知が欠落した際の復旧、期限切れ後の遅延通知、キュー読み取り中の状態変更と失敗からの再試行を検証する。実Serviceからアダプターへの効果の接続と連続再生は [#83](https://github.com/4rtofl/Audipp/issues/83) の範囲。実機と実サービスの動作確認は未実施。
